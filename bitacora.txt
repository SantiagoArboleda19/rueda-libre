Minireto 8: Contraste y mapa de uso del color
1. Clasificación de las combinaciones de color

Según los criterios de accesibilidad WCAG nivel AA, las combinaciones se clasifican de la siguiente manera:

    Blanco (#FFFFFF) sobre Verde Ruta (#1E7A4F): ratio de 5.31:1. Apta para texto normal y grande.
    Blanco (#FFFFFF) sobre Naranja Pedal (#F39A2B): ratio de 2.22:1. No apta para texto normal ni grande.
    Azul Noche (#14213D) sobre Naranja Pedal (#F39A2B): ratio de 7.20:1. Apta para texto normal y grande.
    Azul Noche (#14213D) sobre Crema (#FAF6EF): ratio de 14.83:1. Apta para texto normal y grande.
    Gris Asfalto (#5B6470) sobre Crema (#FAF6EF): ratio de 5.57:1. Apta para texto normal y grande.
    Verde Ruta (#1E7A4F) sobre Crema (#FAF6EF): ratio de 4.93:1. Apta para texto normal y grande.
    Naranja Pedal (#F39A2B) sobre Crema (#FAF6EF): ratio de 2.06:1. No apta para texto normal ni grande.
    Blanco (#FFFFFF) sobre Azul Noche (#14213D): ratio de 15.97:1. Apta para texto normal y grande.

Conclusión: seis combinaciones son aptas para texto normal y grande, y dos no son aptas para texto de ningún tamaño según el nivel AA.
2. Mapa de uso del color

    Texto principal: utilizaré Azul Noche (#14213D) sobre el fondo Crema (#FAF6EF), porque ofrece un contraste de 14.83:1 y
    facilita la lectura.
    Texto secundario: utilizaré Gris Asfalto (#5B6470) sobre Crema (#FAF6EF), con un contraste de 5.57:1.
    Fondos: utilizaré Crema (#FAF6EF) como fondo general de la página, porque es un color suave que permite combinarse con textos
    oscuros y mantener una buena legibilidad.
    Botones principales: utilizaré Verde Ruta (#1E7A4F) con texto blanco (#FFFFFF), ya que su contraste es de 5.31:1 y cumple los
    requisitos para texto normal.
    Botones secundarios: utilizaré Naranja Pedal (#F39A2B) con texto Azul Noche (#14213D), porque su contraste de 7.20:1 garantiza
    una buena legibilidad.
    Enlaces: utilizaré Verde Ruta (#1E7A4F) sobre el fondo Crema (#FAF6EF), con un contraste de 4.93:1. Además, los enlaces tendrán
    un subrayado para que puedan identificarse sin depender únicamente del color.
    Destacados: utilizaré Naranja Pedal (#F39A2B) en elementos decorativos, etiquetas y detalles visuales. Evitaré utilizarlo como 
    texto sobre Crema o con texto blanco, ya que esas combinaciones no alcanzan el contraste mínimo requerido.

La comprobación del contraste me permitió identificar qué combinaciones de colores son accesibles y cuáles debo evitar.
Aprendí que no basta con elegir colores que se vean bien juntos, sino que también deben facilitar la lectura y la navegación.

Por eso, utilizaré Azul Noche y Gris Asfalto para los textos, Crema para los fondos, Verde Ruta para los botones principales y

Uso de Flexbox y Grid

1. Portada – Grid

Se utilizó CSS Grid mediante grid-template-columns: repeat(auto-fit, minmax(250px, 1fr)). Se eligió porque permite distribuir la imagen y la descripción en columnas, adaptándose al espacio disponible. Cuando no hay suficiente espacio horizontal, los elementos pasan automáticamente a otra fila.

2. Galería de bicicletas – Grid

Se utilizó CSS Grid mediante grid-template-columns: repeat(auto-fill, minmax(23rem, 1fr)). Se eligió porque permite organizar las tarjetas de bicicletas en varias columnas y filas, manteniendo una distribución uniforme y adaptable al tamaño de la pantalla.

3. Reservas – Sin Flexbox ni Grid en el contenedor principal

El formulario se organizó utilizando el flujo normal de los elementos HTML. Se utilizaron etiquetas fieldset para separar y agrupar los datos personales, la información de la reserva y la confirmación. Esto permite mantener una estructura clara y ordenada.

4. Fila del formulario – Flexbox

Se utilizó Flexbox mediante display: flex, gap y flex-wrap: wrap en .subseccion-tusdatos. Se eligió porque permite ubicar los campos del formulario horizontalmente, distribuir el espacio entre ellos y hacer que pasen a otra línea cuando no hay suficiente espacio.

5. Encabezado – Flexbox

Se utilizó Flexbox mediante display: flex, align-items: center y justify-content: space-between en .menu. Se eligió porque permite distribuir el nombre de la página y el menú de navegación en una misma fila, manteniendo una separación adecuada. También se utilizó flex-wrap: wrap para facilitar la adaptación a pantallas pequeñas.

6. Pie de página – Flexbox

Se utilizó Flexbox mediante display: flex, justify-content: space-around y align-items: center. Se eligió porque permite distribuir horizontalmente el nombre del proyecto, el correo electrónico y el año, manteniendo una alineación vertical y una separación uniforme.

Comparativa: Bootstrap vs Tailwind CSS

Durante el desarrollo de Rueda Libre tuve la oportunidad de conocer y repasar conceptos de Bootstrap y posteriormente trabajar de manera más profunda con Tailwind CSS. Aunque Bootstrap se abordó principalmente de forma introductoria y no se implementó ampliamente en el proyecto, este acercamiento permitió identificar algunas diferencias entre ambas herramientas y comprender sus principales características.

1. Curva de aprendizaje

Bootstrap permite construir interfaces rápidamente mediante componentes y clases predefinidas. Su aprendizaje inicial resulta sencillo porque ofrece estructuras listas para utilizar.

Tailwind requiere familiarizarse con sus clases de utilidad y comprender cómo combinarlas. Al principio puede parecer más complejo, pero permite controlar cada detalle de los elementos.

2. Personalización

Bootstrap ofrece componentes con estilos establecidos que se pueden modificar mediante CSS. Sin embargo, cuando se necesita una apariencia muy específica, es posible tener que sobrescribir varios estilos.

Tailwind facilita la personalización directamente desde el HTML mediante clases de utilidad. En Rueda Libre pude adaptar colores, tipografías, distribución, estados y modo oscuro utilizando la configuración de la marca.

3. Tamaño final

En la landing de Rueda Nocturna, el CSS minificado generado con Tailwind tuvo un tamaño de [15,58 KB].
En la landing de Rueda Rueda Libre, el CSS puro tuvo un tamaño de [13,45 KB].

En este proyecto no se realizó una implementación completa de Bootstrap ni se incorporó su JavaScript, por lo que no se cuenta con una medición propia de estos recursos dentro de Rueda Libre. La comparación se centra principalmente en el CSS generado por Tailwind frente al CSS desarrollado anteriormente de forma manual para el proyecto.

El resultado permite observar cómo cambia el tamaño de los estilos al pasar de una implementación con CSS propio a una basada en Tailwind y su proceso de minificación.

4. Casos de uso

Bootstrap resulta conveniente cuando se necesita desarrollar rápidamente una interfaz utilizando componentes comunes y una estructura visual consistente.

Tailwind es una buena alternativa cuando se busca construir una interfaz personalizada, controlar los estilos con precisión y mantener una configuración visual propia.

Recomendación para Rueda Libre

Para Rueda Libre recomiendo Tailwind CSS porque el proyecto necesita una identidad visual propia, con colores, tipografías, componentes y diseños adaptables a diferentes dispositivos.

Además, su sistema de utilidades permite personalizar los elementos directamente en el marcado y reutilizar patrones mediante @apply cuando existen estilos repetidos, como ocurre con los botones de Rueda Nocturna.

Pruebas del formulario de inscripción – Rueda Nocturna

Se realizaron pruebas de funcionamiento, validación y accesibilidad del formulario.

1. Envío con campos vacíos

Se intentó enviar el formulario sin ingresar información. El navegador impidió el envío y solicitó completar los campos obligatorios gracias al atributo `required`.

2. Envío con datos inválidos

Se probaron diferentes valores que no cumplían las condiciones establecidas:

- Nombre: no permitió ingresar nombres con menos de 3 caracteres.
- Correo electrónico:** exigió un formato válido que incluyera el símbolo `@`.
- Celular: rechazó los números que no cumplían el patrón definido.
- Demás campos: se verificaron las restricciones establecidas para las opciones y los valores permitidos.

El navegador impidió el envío mientras existían datos inválidos.

3. Envío con datos completos y válidos

Se completaron todos los campos con información válida. El formulario permitió enviarlo y la página se recargó.

Sin embargo, se identificó que actualmente no existe un servidor ni una base de datos conectados para almacenar las inscripciones. Por lo tanto, la prueba confirma que funciona la validación del formulario, pero no que la información quede registrada.

4. Prueba de accesibilidad

Se recorrieron los campos utilizando únicamente el teclado. Se comprobó que es posible navegar por los controles del formulario y completar sus campos sin utilizar el mouse.

Conclusión

El formulario cumple con las validaciones HTML solicitadas y permite la navegación mediante teclado. Queda pendiente una conexión con un servicio backend para recibir y almacenar las inscripciones.
